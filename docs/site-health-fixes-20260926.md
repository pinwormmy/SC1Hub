# 사이트 오류 수정 — 2026-09-26

## 확인한 원인과 수정

- 운영 `BoardMapper.countTotalPost` 오류 쿼리는 `where and notice=0`이었다.
  지원하지 않는 `searchType`이면 검색 조건의 모든 `<if>`가 빠지는 것이 원인이다.
  서비스에서 허용된 검색 유형 이외의 값을 `title`로 정규화하고,
  매퍼에서도 `<choose>/<otherwise>`로 기본 조건이 항상 생성되도록 수정했다.
- 본문/제목+본문 검색의 OR 조건을 괄호로 묶었다.
  검색된 공지글이 `notice=0`을 우회해 일반 목록과 건수에 포함되던 문제를 막는다.
- 로그의 숫자 파라미터 타입 오류와 DTO 바인딩 실패는 500 대신 400으로 처리한다.
  원본 입력값을 로그/응답에 포함하지 않고 한 줄 WARN만 남긴다.
- 별도 저장 오류는 `funboard.CONTENT`의 `Incorrect string value`였다.
  읽기 전용 메타데이터 조회로 등록된 게시판 15개의 TITLE, WRITER, CONTENT,
  search_terms가 모두 3바이트 `utf8`임을 확인했다.
  해당 컬럼에는 인덱스가 없고, 제목/작성자는 각각 VARCHAR(100)/VARCHAR(30) NOT NULL,
  본문/검색어는 TEXT NULL이었다.
  `src/main/resources/sql/20260926_upgrade_post_text_utf8mb4.sql`은 이 구조를 유지하며
  네 컬럼의 문자셋만 `utf8mb4`로 바꾼다. 검색어도 본문에서 파생되므로 함께 변경한다.

## 검증

- 수정 전 새 매퍼 회귀 테스트 9개 중 8개 실패로 SQL 문법 오류와 공지글 혼입을 재현했다.
- 수정 후 관련 매퍼/서비스/예외 처리 테스트 통과.
- `./gradlew clean build`: 전체 479개 테스트 통과, 실패/오류/건너뜀 0개.
  JSP 사전 컴파일 오류 0개, WAR 검증 통과.
- 격리된 임시 MySQL 9.6.0에 운영과 같은 문자 컬럼 구조를 생성해 문자셋 SQL을 검증했다.
  15개 테이블/60개 컬럼, 두 번 적용, 기존 한글/NULL 보존,
  네 컬럼 모두 이모지 저장·조회 확인. 임시 서버와 데이터는 종료·삭제했다.
  운영 MariaDB에서의 DDL 실행 검증은 아직 하지 않았다.
- `git diff --check` 통과.

## 적용 상태

- 기본 체크아웃 `main`의 로컬 수정이며 커밋/푸시/배포는 하지 않았다.
- 기존 AGENTS.md 변경 및 다른 감사 문서 디렉터리는 유지했다.
- 운영 DB에는 조회만 수행했으며 문자셋 SQL은 적용하지 않았다.
  이 SQL은 시작 시점이나 deploy.sh에서 자동 실행되지 않는다.
- 운영 반영 시 대상 테이블 백업과 현재 컬럼 구조를 확인한 뒤 문자셋 SQL을 적용하고,
  해당 릴리스 커밋의 최종 빌드/푸시/배포 및 서버·공개 페이지 검증을 수행해야 한다.
  ALTER TABLE은 암묵적 커밋과 테이블 잠금을 수반한다.
  4바이트 문자가 저장된 후에는 기존 utf8로 되돌리면 데이터 손실 위험이 있다.
